1  Your own repo

First, why any of this exists

You are writing a poem. You save it as poems.txt.

You change a line. You want the old one back, just in case. So you save a copy. poems_v2.txt. Then poems_final.txt. Then poems_final_ACTUAL.txt.

Another problem

You save Diff_file_0_file_1.txt. You feel proud of yourself for a second.

Now do it again for file_1 and file_2. And again for file_0 and file_2, just in case you need to compare those too.

Three files. Three diffs. And you have barely started the poem.

Now imagine this is not a poem. Imagine it is twenty files, for a real project, and every single one needs its own diff, against every other version of itself, forever.

You are not writing poems any more. You are writing paperwork about poems.
Try again?

Okay, new idea. Forget the separate diff files. Just keep one file, changelog.txt, and every time you save, add a line about what you did.

Fixed the roses line. Added a new stanza. Changed the ending, felt too sad.

One file. One place to check. Feels almost responsible.

But

Read that second line again. "Fixed the roses line."

Fixed it how? What did it say before you fixed it? You do not know. You did not write it down. You wrote that you changed something, not what it used to be.

And be honest. The day you were tired, or in a hurry, or just forgot? You did not update the changelog that day either. You know you did not.

It is not a record. It is a note you are hoping you can trust later.
One more problem

Your friend actually likes your poem. They want to add a line.

You send them poems.txt. They add something beautiful, save it, and email it back as poems_returned.txt.

Except, while you were waiting for them to reply, you kept writing too. You added your own line. You have your version. They have theirs.

Both of you did something right. Neither of you did anything wrong.

So which file is the poem now?
A solution? Maybe?

Fine. Open both files side by side. Read every single line of both. Find what is different. Carefully copy the good parts into a new file.

Call it, of course, poems_merged_v2_final.txt.

You did it. It is late, your eyes hurt from comparing two identical-looking paragraphs for the fifteenth time, but you did it.

The truth

You will miss a line eventually. Not because you are careless, but because comparing two versions of anything by eye, line by line, for long enough, is exactly the kind of task humans are bad at and do not notice they are bad at.

Your friend's favourite line, the one they were proudest of, quietly does not make it into the merged file. Nobody meant for that to happen. It just did.

And now think about doing this every time either of you saves. Now think about doing it with three friends. Five.

Let us be honest with ourselves

Look back at everything you just tried. Naming files "final". Numbering them. Writing diffs by hand. Keeping a changelog. Comparing two files line by line at midnight.

Every single one of them needed you, a tired, distracted, forgetful human, to do the right thing, perfectly, every single time, forever.

One tired night. One missed line. One overwritten file. That is all it takes to lose hours of work you cannot get back.
What if

What if you did not have to remember any of this?

What if something kept every version, automatically, the moment you saved, with no renaming required?

What if it could tell you exactly what changed, down to the line, without you writing a single diff by hand?

What if two people could edit the same file, at the same time, and it figured out how to combine both of your work, without either of you losing a line?

Sit with that question for a second before you answer it.

Then open your terminal. That is the rest of today.

What just got wired up: origin, upstream, and the three kinds of branch


  
An upstream is a tracked link between a local branch and a
  remote branch. It tells git that when you run git push or
  git pull, this is the remote branch you should talk
  to.


  
Three types of branch:

  

    
KindWhere it lives

    
Local branchOn your machine. What you work on.

    
Remote-tracking branch
        On your machine, read only. A snapshot of the server, updated when you
            run git fetch. This is origin/main.

    
Remote branchOn the GitHub server. The real thing.

  


  
origin is just a nickname for a URL, and it is
  per folder, not global. Every repo on your machine can have a
  remote called origin pointing somewhere different. Git looks it up
  in .git/config.


  


  
Why a short name matters. Without one you would push like
  this, every time:

  
git push https://github.com/{{user}}/my-first-repo.git main

  
With one, and after setting the upstream once, it is just:

  

  
The one-time setup is git push -u origin main. The
  -u is what creates the tracked link. --push in step 5
  did it for you.

  Step 4

    Why the filename rule exists
    Your GitHub username is unique, so no two people can create the same file, so
    no two pull requests can touch the same line. Thirty PRs will merge in a row
    without a single conflict. That is deliberate. Phase 3 removes the safety net.

  Step 5
  
The conflict moment

  
The first PR merges cleanly. Everything is fine. It will not be fine for
  anybody else. GitHub will say:

  
This branch has conflicts that must be resolved

  

    Nothing has gone wrong
    Your branch was built on a version of main that no longer exists.
    Somebody else's line is now where yours was, and git will not guess which of
    you should win. This is git asking you a question, not reporting an error.

  Step 6
  
Read the markers

  
<<<<<<< HEAD
1. Name: Ananya   Language: JavaScript
=======
1. Name: Rahul    Language: Python
>>>>>>> main

  

    
MarkerMeans

    
<<<<<<< HEADYour version, on your branch

    
=======The dividing line

    
>>>>>>> mainThe version already on main

  

  

    The bit everyone gets wrong
    A conflict feels like a question of who wins. Almost always the right answer
    is both. You want Rahul's line and yours. Delete the
    three marker lines and keep both entries.
  

  
The markers are just text git inserted. Nothing is watching them. Edit the
  file until it reads the way it should, then:

  

  

    git add is how you say "resolved"
    There is no separate resolve command, which surprises people. Staging the
    file is the resolution.
  

  
Stuck or panicking? You can always back out and start again. Nothing is
  lost:

  






  Step 7
  
Review and merge each other's work

  

  

    The golden rule: one PR at a time
    After a merge, the next person pulls main, resolves their
    conflict, and only then merges. If five people merge at once,
    main becomes a mess and the last person faces a five-way conflict
    nobody can untangle. Go around the table one by one.

Help


Type the error you are seeing.





  
What you seeWhyFix


  
Permission denied on push
      You cloned the original repo, not your fork
      git remote set-url origin https://github.com/{{user}}/git-started.git


  
Permission denied in Phase 3
      You have not accepted the collaborator invitation
      gh api user/repository_invitations then
          gh api -X PATCH user/repository_invitations/ID


  
'add.' is not a git command
      Missing space
      git add . with a space, or name the file directly


  
unknown command "accept" for "gh repo"
      gh repo accept does not exist
      Use gh api user/repository_invitations, or accept in the browser


  
fatal: not a git repository
      You are not inside the project folder
      cd into it. pwd shows where you are.


  
error: pathspec did not match
      Forgot -c or -b, so git looked for an existing branch
      git switch -c add-{{name}}


  
PR opened against your own fork
      Forgot --repo in Phase 2
      gh pr create --repo accelerate-muj/git-started


  
remote upstream already exists
      You added it twice
      Harmless. Ignore it, or git remote remove upstream and re-add.


  
! [rejected] main -> main
      Somebody pushed before you
      git pull origin main then push again


  
CONFLICT (content): Merge conflict in ...
      Two people changed the same lines. Expected in Phase 3.
      Edit the file, keep both, delete the marker lines, git add ., commit


  
Leftover <<<<<<< in the file
      You missed a marker when resolving
      Search the file for <<< and delete every marker line


  
refusing to merge unrelated histories
      The two histories share no common commit
      git pull origin main --allow-unrelated-histories


  
"There isn't anything to compare"
      You committed to main instead of your branch
      git switch -c add-{{name}} then push that


  
gh pr merge fails
      The PR still has conflicts
      The author resolves them first, then merge


  
Git asks for a password and rejects it
      GitHub removed password auth for git in 2021
      gh auth login again, say yes to the git credentials question


  
gh: command not found
      Your terminal cached the old PATH
      Close the terminal and open a new one


  
Stuck in a text editor you cannot exit
      It is vim
      Press Esc, then type :wq and Enter


  
You want to undo the merge and start over
      Nothing is lost. Ever.
      git merge --abort






  Nothing here matches?
  Run git status. It tells you where you are and what git thinks is
